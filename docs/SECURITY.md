# Security model and limitations

**Status: pre-release, unaudited.** Use synthetic accounts only until the whole system, especially BLE and platform integrations, receives independent security review and hardware tests.

## Prior-version dialog-focus defect

Version 0.2.0 could move focus back to the profile-name field after a user had chosen another field; rapidly typed sensitive text could consequently be saved and displayed as a profile name. Version 0.2.1 moves initial dialog focus synchronously and includes a deterministic regression test. If you used an earlier build, inspect profile names for accidentally entered secrets and treat any affected secret as exposed. See [release notes](RELEASE_NOTES.md) for remediation and limitations. This fix is not an independent security review.

## Assets, adversaries and controls

| Threat | Controls | Residual risk |
|---|---|---|
| Lost disk or encrypted backup | PBKDF2-SHA-256, 600k iterations; random 16-byte salt; AES-256-GCM with random 96-bit IV and context-bound AAD | Offline passphrase guessing remains possible. A weak or reused passphrase defeats the KDF. Metadata includes KDF version/salt/ciphertext sizes. |
| Wrong site or port | Exact canonical scheme/host/port checks on selection, capture, vault lookup and immediately in the content script; optional host permission | Host permissions may cover all ports; exact-origin checks are application-level. A compromised legitimate site receives its own filled credentials. DNS/TLS trust and lookalike domains remain user responsibilities. |
| Malicious web page or CSRF | No external message listener or web-accessible extension resources; internal message sender/extension-page checks; commands cannot be invoked by web content; content only receives a manually approved fill or a fill covered by a short-lived explicit opt-in | A page can manipulate its DOM, trick the user into approving a fill, or execute scripts on the same origin. GhostState does not submit forms, but a website can react to input events, submit automatically, or send any filled values elsewhere; review the site before approving a fill. Site-provided DOM and challenge detection are untrusted. |
| XSS in UI | Strict extension CSP, escape dynamic values, `textContent` for errors; synthetic XSS browser test | The dashboard uses dynamic `innerHTML`; Mozilla's linter flags three sinks. Escaping and CSP do not replace independent review. Do not add unescaped data. |
| Other extensions / compromised browser or OS | Separate extension origin, no exposed external API, non-extractable in-memory CryptoKey | A malicious extension, debugger, accessibility tool, malware, compromised browser or same-user process may observe typed or filled credentials. No software vault can protect against a fully compromised endpoint. |
| BLE passive observer or active MITM | Ephemeral X25519, transcript-bound HKDF, code comparison, HMAC confirmations, AES-GCM, HMAC receipt | An eight-digit SAS has limited entropy; users must compare it through a trusted channel and reject mismatches. Radio metadata/device addresses and the public handshake are observable; denial of service is possible. No independent protocol audit or real-radio validation yet. |
| Replay/expired/downgraded grant | Version/purpose/session binding, authenticated ciphertext, unique ID replay set, expiry ≤120 s, new session keys on restart | Replay set is in memory and scoped to the session. New sessions cannot decrypt old ciphertext. Clock skew can reject legitimate grants; denial of service is possible. |
| Unauthorized native calls | Per-browser exact allowlist plus executable caller allowlist, bounded native frames and strict command schemas; no generic shell/file command | Same-user software can launch/spoof a command line or modify a user's own config. OS accounts, filesystem protection, browser installation and malware resistance are necessary. |
| Native or UI secret persistence | Native secrets/session grants are ephemeral and not intentionally stored; plaintext master passphrase is never saved; only encrypted backup exported | Plaintext credentials pass over the local browser-native pipe and exist in process memory; zeroization is best effort (JS strings, JSON and OS copies cannot be guaranteed wiped). Crash dumps, swap, debugging and screen capture can expose data. |
| Opt-in automatic fill | One chosen profile/tab, ten-minute in-memory authorization, unlocked vault, exact origin and learned state, top frame, focused/visible page and sampled field visibility, empty mapped fields, same-origin form action, challenge checks, one delivery per document/state | Disabled by default. A compromised site on the approved origin can still steal or submit filled credentials. Challenge heuristics can miss checks; site script can change behavior. A delivery already in flight cannot be revoked retroactively. |
| Plaintext import and clipboard | Explicit local file selection, review and master-passphrase check; only supported login fields persisted. Reveal/copy requires fresh authentication | CSV exports remain readable on disk; JS memory, clipboard history, screen capture or compromised endpoints can retain secrets. Unsupported columns are ignored, not imported. |
| CAPTCHA / OTP | No submit automation or OTP capture; heuristic challenge detection pauses | Detection is best effort; users must recognize and handle all challenges manually. The program cannot guarantee every challenge is detectable. |

## Permission rationale

Required: `storage` for transient selected-tab state; `activeTab` for an explicitly selected tab; `scripting` for explicitly initiated content injection and scoped, opt-in automatic attempts. The manifest declares optional HTTPS host patterns and loopback HTTP patterns so the browser can request an individual host only at the user's gesture; there is **no required broad host access**, `cookies`, `tabs`, `history`, or `externally_connectable` permission. Optional `nativeMessaging` is requested when connecting the companion. Firefox's optional `authenticationInfo` declaration/consent covers the explicitly requested credential transfer outside the add-on. Browser site permission can be revoked in Privacy & security or in browser settings.

Some Chromium versions do not expose `connectNative` in an already-running worker immediately after an optional grant. In that case the dashboard opens a **bundled local extension frame**, not a remote resource. The worker accepts only the expected extension-page URL in a child frame of the requesting tab, with a short-lived, random, one-use challenge; it validates request operations before relaying to the fixed native-host name. The frame is not declared web-accessible. The credential still travels in plaintext within extension/native local messaging. Closing the dashboard that owns this fallback frame disconnects the host; keep that dashboard open and reconnect if necessary. These are defensive controls tested with synthetic data, not an independent audit.

## Storage and recovery

There is no remote recovery. An encrypted backup without its passphrase is not recoverable. The passphrase is not stored, synced or transmitted. Exported ciphertext should still be treated as sensitive. Deleting a profile updates the encrypted vault, but browser/database/filesystem snapshots may retain prior ciphertext; cryptographic deletion of old backups is not guaranteed. Automatic locking is activity-based (1–30 minutes); service-worker suspension can lock sooner. A session-generation check rejects operations whose vault was locked or re-unlocked during decryption. A fill or transfer already handed to the browser/native host may finish while a lock is in progress; lock is not a retroactive revocation of data already delivered. Locked status removes the live key reference, but garbage collection and physical memory clearing are not guaranteed.

The native host stores no long-term keys or credentials and therefore does not require OS keychain storage in this build. The non-secret allowlist is filesystem-protected. If future designs persist native identities or secrets, use the OS keychain/credential manager; do not store plaintext files.

## Release gates still outstanding

- Independent cryptography and browser-extension security review, fuzzing and broader adversarial testing.
- Physical two-device BLE tests, real grant timing, reconnect, loss, MTU, concurrency and OS Bluetooth permission tests.
- Firefox transfer using physical devices; actual macOS/Windows installation, hardware, WinRT peripheral callbacks and permission flows; Safari's native bridge. The unsigned Windows binary was only cross-compiled and exercised under Wine for protocol/native framing, not actual Windows Bluetooth. Firefox synthetic workflow, native-host connection, and real prompts have been exercised as described in the test status.
- Signing, notarization, store review and a legitimate production Firefox add-on ID. The included ID is for local development only.

The Chromium optional-native-permission test uses the real browser prompt, unmodified extension and registered Linux host, including rejection of unarmed, wrong-tab, wrong-token and replayed fallback frames. A separate prompted test sends only synthetic credentials through a **mock** host; it is not a Bluetooth test. Other headless integrations use test-only pregranted localhost/native manifests; see `tests/e2e` and [DEVELOPMENT_STATUS.md](../DEVELOPMENT_STATUS.md).

## Automatic-fill risk and cloud backup

Automatic filling is off by default. An authorization covers one learned profile and selected tab for at most ten minutes, is memory-only, and requires an unlocked vault. It is not equivalent to per-fill approval. A compromised site, same-origin malicious script or endpoint malware can read values; never enable it on a site you do not trust. Use [manual cloud backup instructions](CLOUD_BACKUP_AND_SYNC.md); automatic cloud sync is not implemented. The basic password health check does not test for breached credentials.
