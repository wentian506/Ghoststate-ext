# Architecture and data flows

## Boundaries

```text
User -> extension dashboard/popup (trusted extension origin)
          | approved commands only
          v
    MV3 background / local IndexedDB -- encrypted whole-vault record
          | user selects exact origin; grants per-host access
          v
    isolated content script -> structural scan -> SHA-256 fingerprint
          | approved, exact-match fill only; never automatic submit
          v
    selected top-level website

Dashboard -> native messaging (browser allowlist + host caller allowlist)
          -> Rust companion -> BLE GATT -> nearby Rust companion
          -> explicit recipient acceptance -> receiving local vault
```

A standalone dashboard at the Vite development URL uses its own IndexedDB and the same local vault module, but cannot select/inject into sites or reach native messaging. It is a preview/development workspace, not a connected remote service. No web backend is required.

## Fingerprints and workflow

`packages/dom-fingerprinter` observes visible top-level inputs, buttons, selects and textareas. It creates a normalized sequence of tag, allowlisted input type/role/autocomplete category, depth and allowlisted-tag sibling-index path, hashing canonical JSON using SHA-256. Unknown and custom element names are collapsed to a generic `element` token so site-provided tag names are not stored; nodes more than 20 ancestors deep are skipped rather than creating ambiguous truncated paths. Temporary DOM attributes can provide classification and challenge hints, but attribute strings, values, text, HTML, screenshots, full URL paths and queries are not stored. The UI stores the structural vectors and approved username/password mappings inside the encrypted vault. CSS/class/id/value/text changes alone do not affect the hash; DOM rearrangements can.

A `MutationObserver`, popstate/hashchange listeners and a one-second location comparison handle live and SPA changes. Ordinarily the background injects only for an explicit scan of the selected exact-origin tab. An explicit, in-memory automatic-fill authorization can additionally trigger fresh scans for that **one selected tab and one learned profile**, for up to 10 minutes while the vault is unlocked; it does not grant broad host permissions. Tab activation, window focus, completed navigation and value-free observations may trigger an attempt. The background never uses an observation as a credential request: it rechecks the selected tab, focused window, optional host permission and exact origin, then performs a fresh scan and exact state/transition match. The top-frame content script independently checks a per-document random ID, visibility/focus and sampled unobstructed-field hit tests, challenge heuristics, live field targets, empty values and same-origin form actions. It checks emptiness locally but does not transmit or save the preexisting values. A state is filled at most once per document in an authorization, with a maximum of 50 document/state deliveries. Automatic scans, vault reads and automatic activity logging do not extend vault idle time. The in-memory grant expires on timeout, lock, worker restart, explicit disable, target reselection, site-permission revocation and relevant profile/workflow mutations. A navigation to another origin is not filled; the grant may resume if the selected tab returns to the authorized origin before expiry. An operation already handed to the browser may finish during a concurrent lock.

Clearing the target, choosing another tab or manually locking stops the former tab's observer where reachable. A state capture is explicit, checks that the UI-reviewed fingerprint still matches, and increments the workflow version; edges are manual submission/navigation. Exact matches only can fill. A different or low-confidence screen pauses; similarity is diagnostic and is never sufficient to release credentials. An ephemeral execution cursor checks recorded edges, allows retry and an explicit return to the first state; it resets when the worker goes away or a new site is selected. Manual mode requires individual approval; automatic mode requires prior, temporary user opt-in. Cross-origin redirects must be separately selected/authorized and cannot receive another origin's secret. A malicious page on the approved origin may read filled fields or respond to input events, including submitting itself; GhostState does not call submit.

Only top-frame visible fields are supported: cross-origin or same-origin frames, shadow roots, closed/custom controls and some web components are not captured. Challenge detection is heuristic and cannot guarantee identification of every OTP, CAPTCHA, passkey or security question. Do not map challenges as credentials. GhostState never solves a challenge or intercepts a typed OTP.

## Vault

`packages/vault` stores a non-secret header (schema, random 16-byte salt, PBKDF2 parameters, encrypted verifier) and one encrypted JSON vault record in IndexedDB. Each write uses a new 12-byte random AES-GCM nonce and domain-separated additional authenticated data. The non-extractable 256-bit key is derived with PBKDF2-HMAC-SHA-256 (600,000 iterations) and held only in memory until lock, timeout or background unload. An encrypted export includes the header and ciphertext, not a recovery key. A lost passphrase cannot be recovered. Decrypted vault contents and backups are schema-validated and bounded before use or persistence. Operations are serialized within the background instance; a standalone web preview tab has its own independent instance and is not a cross-tab concurrency service.

The vault encrypts origins, credentials, workflow states, mappings, settings and a bounded optional operation log as one record. Origin-scoped lookup checks the exact origin again in the background and immediately before fill in the content script. The content script cannot query credentials; the trusted extension worker sends only the values required for the approved state. As with all browser autofill, the target website can read whatever the user chooses to fill.

### Local password management and import

Generation uses Web Crypto rejection sampling and a bounded length/character-set selection; generated values are not saved until the user saves a profile. Local health checks compare passwords within the decrypted vault and flag limited weak patterns, without a breach lookup. `REVEAL_PROFILE`, `UPDATE_PROFILE` and `IMPORT_PROFILES` require re-entering the master passphrase and retain a vault-generation lease. Revealed values are shown only in a trusted extension dialog, with an explicit clipboard action and a short display timeout; JS strings and system clipboard history cannot be reliably zeroized. Origin changes discard learned workflows. A user-selected plaintext standard or Bitwarden login CSV is parsed locally with bounded sizes, reviewed without showing passwords, and imported atomically; only label, exact origin, username and password persist. Unsupported columns, including OTP seeds and notes, are not imported. Exact origin/username duplicates are skipped; the 200-profile vault cap remains. See [comparison](PASSWORD_MANAGER_COMPARISON.md) and [cloud guidance](CLOUD_BACKUP_AND_SYNC.md).

## Native messaging and BLE

Native host messages are bounded, JSON-schema checked and restricted to an allowlisted command set. The browser host manifest identifies allowed extension origins/add-on IDs; the executable separately checks browser launch arguments against `~/.config/ghoststate/allowed-callers.json` (on Windows, `%USERPROFILE%\.config\ghoststate`). These checks do not protect against malicious code running as the same OS user. On Firefox the background additionally verifies that optional authentication-info consent remains granted before a credential send or acceptance.

`btleplug` provides the central (scanner/client) role on Linux, macOS and Windows; it does **not** provide a GATT peripheral. The receiving/advertising role is implemented with BlueZ `bluer` on Linux and experimentally with WinRT `GattServiceProvider` on Windows. Windows was cross-compiled on Linux, but its WinRT callbacks, OS permissions and advertising have not been validated on real Windows or hardware. There is no macOS receiver or mobile app. A real adapter and OS Bluetooth service are required; `listen` expires after five minutes. Each session is ephemeral: X25519 keys and random nonces form a versioned transcript; HKDF-SHA-256 derives separate AES-256-GCM and HMAC confirmation keys plus an eight-digit short authentication string (BLE protocol v2; v1 peers are rejected without downgrade). Both users compare and confirm the code; HMAC proofs bind confirmations and grant receipts to the transcript. The remote recipient must confirm before the sender is marked verified.

The sender can maintain at most eight independent central client slots, each with a unique ephemeral session and separate user verification. Peer IDs route requests but are not trusted identities. Each send requires an explicit peer ID and approved profile; there is no broadcast. The Linux and experimental Windows peripheral listeners admit one transport owner/session at a time and keeps at most eight pending short-lived grants. Hardware/OS limits may be lower. The sender explicitly chooses an origin-scoped profile; the credential passes through a local native-messaging pipe and is encrypted before BLE. A grant contains purpose `credential-reauthentication`, a random grant ID, session ID, exact origin, issued/expiry (max 120 seconds) and the credential. The receiver checks version, authenticated encryption, session, purpose, origin, expiry and replay cache before showing metadata. Expired pending grants are removed on the companion's periodic sweep (up to five seconds later). It keeps a pending grant only in memory; explicit recipient acceptance imports it into that receiver's encrypted vault. Session keys and grants are not persisted by the native host. A new pairing after restart uses a different key and rejects prior ciphertext. The client then authenticates locally; this is not an identity-provider-issued grant and is not a transferable authenticated session.

BLE traffic is framed into ≤20-byte ATT chunks with strict order and bounded reassembly. No physical Bluetooth hardware was available for validation: adapter/OS-specific discovery, MTU behavior, interference, connection lifecycles and delivery reliability remain unverified. Static protocol tests are not a substitute for real radio tests or independent cryptographic review.
