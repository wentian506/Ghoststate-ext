# Internal API (GhostState 0.2.2; BLE protocol 2)

These are internal interfaces, not a stable public API. Runtime messages must originate from the extension’s own dashboard or popup; no external listener or web-accessible extension resource is registered. Errors are returned as `{ok:false,error:string}`. The content script can send only a top-frame `GS_OBSERVATION`; the worker validates its sender and origin, never persists it, and never treats it as authorization to retrieve a vault record. An automatic attempt performs a fresh independent scan and rechecks authorization.

## Vault and UI messages

Dashboard `{type,payload}` commands include `STATUS`, `SETUP {passphrase}`, `UNLOCK {passphrase}`, `LOCK`, `LIST_PROFILES`, `ADD_PROFILE {label,url,username,password}`, `UPDATE_PROFILE {id,label,url,username,password,passphrase}`, `REVEAL_PROFILE {id,passphrase}`, `IMPORT_PROFILES {records,passphrase}`, `DELETE_PROFILE {id}`, `LIST_EVENTS`, `CLEAR_EVENTS`, `GET_SETTINGS`, `SET_SETTINGS {minutes,logging}`, `GET_WORKFLOW {id}`, `CLEAR_WORKFLOW {id}`, `EXPORT`, `RESTORE {backup,passphrase}`, and `RESET`.

Reveal, edit and import reauthenticate with the master passphrase and keep the same vault-session lease. `REVEAL_PROFILE` returns that profile’s username and password **only to the trusted dashboard**, which deliberately displays them after the user’s request; it is not exposed to content scripts or arbitrary webpages. Import records accept only `{label,url,username,password}`; they are validated again in the vault, with exact origin/username duplicates skipped and the batch encrypted atomically. The file parser supports standard and Bitwarden login CSV headers and does not persist unsupported columns.

`SELECT_TAB {tabId,origin}` requires a separately granted host permission. `TARGET`, `CLEAR_TARGET`, `SCAN`, `RECORD_STATE {id,fingerprint,mappings}`, and `FILL_STATE {id}` apply to the selected exact origin. `AUTO_ENABLE {id}` explicitly authorizes one selected profile and tab for at most ten minutes; `AUTO_STATUS` reports only non-secret authorization metadata, and `AUTO_DISABLE` clears it. The authorization is memory-only, does not survive a worker restart or lock, and is not a substitute for consent. Automatic attempts require a focused window/active tab, exact origin and learned state, browser permission, unchanged vault lease and transition; the top-frame content script verifies a per-document ID, live structure, challenge heuristics, visibility/focus, empty fields and same-origin form action. Each state is automatically filled at most once per document during the authorization. Manual and automatic fills never invoke form submission. A website can react to the input itself.

`NATIVE_CONNECT`, `NATIVE_STATUS`, `NATIVE_DISCONNECT`, and `NATIVE_REQUEST {op,data}` expose only non-secret allowlisted operations. `NATIVE_SEND_PROFILE {id,origin,peerId}` requires a particular, already approved/verified recipient and obtains a credential internally from the vault; `NATIVE_ACCEPT_PROFILE {id,origin,label}` validates the expected incoming origin and saves only after user approval. On Firefox, the background checks that the optional `authenticationInfo` grant remains present immediately before send or acceptance; it fails closed after revocation. Successful manual fill/send responses can include `logFailed:true` if delivery succeeded but the subsequent optional activity update failed.

## Native stdio

Browser native messaging uses a four-byte native-endian unsigned length followed by UTF-8 JSON, max 65,536 bytes. Request: `{id: positive_safe_integer, op: string, payload: object}`. Response: `{id,ok:true,data}` or `{id,ok:false,error}`. Top-level and operation payloads reject unknown fields.

Commands: `status`, `discover`, `listen`, `stop_listen`, `pair {id}`, `confirm_pair {peerId?}`, `cancel_pair {peerId?}`, `incoming`, `reject_transfer {id}`, `send_grant {peerId,origin,username,password}`, `accept_transfer {id}`. For sender operations `peerId` is mandatory; a Linux/Windows receiver’s one listener session uses an empty payload for confirm/cancel. Status includes a bounded `pairings` array, `receiverPairing`, `connectionLimit:8`, and incoming metadata. Peer IDs are transport routing identifiers, **not trusted identities**; compare each short authentication code with its recipient. The extension never forwards arbitrary `send_grant`/`accept_transfer` requests from webpage content. No command executes a shell or accepts a filesystem path.

The host must be launched by an allowlisted browser caller. Chromium passes the extension origin as its first argument; Firefox passes the host manifest path followed by the add-on ID. These strings are checked against the local allowlist in addition to the browser’s host-manifest check. Same-user command-line spoofing is outside this boundary.

## BLE protocol v2

Service UUID `77ec8a7c-4a0f-4b93-b9cb-613dfb0a3201`; write UUID `...3202`; read UUID `...3203`. Messages are JSON fragmented into ATT chunks with a one-byte kind, big-endian two-byte fragment index and count, and ≤15-byte content. A separate three-byte control requests an outgoing fragment. Maximum reassembled message: 12,000 bytes. The first peer owns a Linux/Windows receiver listener until stopped, limiting cross-client fragment mixing but permitting denial of service.

Wire operations: `hello {hello:{version:2,public_key,nonce}}`, `confirm {proof}`, `grant {envelope:{version:2,session,nonce,ciphertext}}`. Version 1 peers are rejected; both sides must update. X25519 keys and nonces, role order and version are transcript-bound; HKDF produces separate AES-GCM and HMAC confirmation keys and an eight-digit SAS. Both users compare and explicitly confirm the entire SAS. Each of up to eight sender slots holds a distinct ephemeral session. HMAC proofs bind confirmations and grant receipts to the session. An AES-256-GCM grant is session- and purpose-bound and is checked for authentication, replay, exact origin and expiry. A Linux or experimental Windows receiver has one session and at most eight pending grants; acceptance is separately explicit. Logical routing and protocol isolation were tested in memory, not with physical Bluetooth hardware.
